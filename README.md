# 씹덕주식

게임을 종목으로 상장시켜 모의 자금으로 거래하는 서비스다. 시세·뉴스·주문 데이터는
Spring Boot와 MySQL이 관리하고, 로그인은 Firebase Google 인증을 사용한다.
백엔드에 연결하기 전에는 화면 확인용 초기 모의 데이터를 표시한다. 현재 화면은 대체 엔진을
계속 실행하지 않으며, 연결 실패 후 자동 시뮬레이션 전환이나 오프라인 주문을 지원하지 않는다.

**현재 상태(2026-09-30 코드 대조 기준)**: 핵심 주문·체결·자산 관리 기능은 구현돼 있다.
가격 변동 설명의 화면 연결, 미션 수행 확인, 가격 알림 발동 등은 보완이 필요하며,
최신 로그인·거래 통합 검증과 서명 APK 배포는 남아 있다.

## 실행

```bash
npm install
npm run dev        # http://localhost:5180
npm run typecheck
npm run build      # dist/ 생성
npm start          # dist/ 를 서빙하는 무의존성 Node 서버 (PORT)
```

### 로컬 백엔드 연결

1. MySQL을 실행하고 `database/schema.sql`을 적용한다.
2. 루트 `.env`에 DB와 Firebase Admin 설정을 둔다. 서비스 계정 JSON은
   `backend/secrets/firebase-admin.json`에 보관하며 Git에 커밋하지 않는다.
3. `scripts/run-backend.ps1`을 실행한다. Spring Boot API는 `http://localhost:8081`에서 열린다.
4. `.env.local`의 `VITE_API_BASE_URL=http://localhost:8081`을 확인하고 `npm run dev`를 실행한다.

웹 Firebase 설정은 `.env.local`의 `VITE_FIREBASE_*` 변수로 읽는다. 배포 시에는 같은 변수를
호스팅 서비스의 빌드 환경변수로 등록하고, 백엔드에는 `FIREBASE_SERVICE_ACCOUNT_JSON`,
`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `GAMESTOCK_CORS_ORIGIN`을 별도 시크릿으로 등록한다.

### 배포

- **Railway 백엔드**: 서비스 루트를 `backend/`로 지정하고 `railway.json`이 해당
  `pom.xml`을 Maven으로 빌드한 뒤 `target/gamestock-backend-0.1.0.jar`를 실행한다.
  헬스체크 주소는 `/api/health`다.
- **Firebase Hosting 프론트엔드**: `npm run build` 결과인 `dist/`를 배포한다.
  프론트의 `VITE_API_BASE_URL`은 Railway 백엔드 공개 주소로 지정한다.
- **프론트엔드 자동 배포**: `.github/workflows/firebase-hosting.yml`이 `main` 브랜치 push마다
  타입체크·빌드 후 Firebase Hosting에 배포한다. GitHub 저장소 Settings → Secrets and variables → Actions에
  Firebase 관리자 서비스 계정 JSON 전체를 `FIREBASE_SERVICE_ACCOUNT` 시크릿으로 등록해야 한다.
- **정적 호스팅(ChatGPT Sites 등)**: `npm run build` 결과인 `dist/`를 그대로 올린다. 클라이언트 라우팅은
  `history.pushState` 기반이므로 서버에 SPA 폴백 설정이 필요하다.

### Expo 앱과 웹 공통 화면

- `mobile/App.js`의 현재 진입점은 `WebMirrorScreen`이며, 웹 화면을 WebView로 표시한다.
- 웹 주소에 `app-shell=1`을 붙여 앱 전용 셸을 유지한다. 공통 거래 화면 수정은 웹 코드에 반영한다.
- 기본 웹 주소는 Firebase Hosting이다. 로컬 웹 변경을 앱에서 확인하려면
  `EXPO_PUBLIC_WEB_APP_URL`을 휴대폰에서 접근할 수 있는 PC의 웹 주소로 지정한다.
  WebView 화면의 API 연결 주소는 해당 웹의 `VITE_API_BASE_URL` 설정을 따른다.
  휴대폰에서 로컬 백엔드에 연결할 때는 API 주소도 PC의 LAN 주소를 사용한다.
- `mobile/`에서 `npm install` 후 `npm start`로 Expo 개발 서버를 실행한다.
- 파일에 남아 있는 `LegacyApp` 네이티브 화면은 현재 진입점에서 사용하지 않는다.
- 공통 화면 코드와 별개로, 실제 기기의 로그인·주문 흐름 및 서명 APK는 추가 검증·배포가 필요하다.

## 화면

| 경로                       | 내용                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `/`                        | 자산 현황 · 게임군 지수 · 기본 투자 미션 · 거래량 상위 시세표 · 뉴스                                 |
| `/market`, `/market/:code` | 서버가 제공하는 종목 시세표 + 정렬·필터(전체/상승/하락/관심)·검색, 종목 상세(차트·주문·체결)         |
| `/news`                    | 종목별 레일 + 날짜로 묶인 속보 피드. 각 소식은 발행 시점 대비 시세 반영률을 함께 보여 준다           |
| `/ranking`                 | 총자산 기준 사용자·참여자 봇 랭킹. 상위 3명은 메달로 순위를 표시한다                                 |
| `/mypage`                  | 닉네임 수정 · 보유 종목·손익 · 체결 내역 · 미체결 주문 취소 · 관심종목 · 가격 알림 등록              |

프론트 종목 정의와 초기 모의 데이터에는 15종목이 있지만, 백엔드가 기본 생성하는 종목은
우마무스메(`UMA`)·블루 아카이브(`BA`)·니케(`GOV`) 3개다. 서버 연결 시 표시되는 목록은
서버 응답과 프론트 종목 정의를 기준으로 결정되므로, 기본 서버 환경을 전체 15종목으로 설명하지 않는다.

메인 제목 클릭과 화면 경로 변경 시에는 스크롤을 맨 위로 이동한다.

## 구조

```
src/
  market/          시세 도메인과 서버 연동
    universe.ts    상장 종목, 호가 단위, 가격제한폭
    engine.ts      로컬 모의 엔진 (현재 화면에서는 초기 스냅샷만 사용)
    newsTemplates.ts  종목별 소재를 쓰는 소식 문구
    selectors.ts   자산 합계, 보유 종목, 정렬, 시세 반영률
    MarketProvider.tsx  Spring API 조회, Firebase 토큰 첨부, 주문 API
  lib/
    firebase.ts    Firebase Web SDK 초기화
    api.ts         Spring Boot 공통 API 호출기
  components/      표현 컴포넌트 (시세표, 주문, 차트, 피드)
  pages/           화면 조합
  router.ts        pushState 기반 5개 화면 라우터 (홈·시장/종목·뉴스·랭킹·마이페이지)
  styles/          tokens → base → chrome/board/market/detail/news (CSS 레이어)
backend/          Spring Boot API·인증·주문 매칭·뉴스 수집·MySQL/JDBC 저장소
mobile/           Expo 앱, 웹 공통 화면을 표시하는 WebView와 앱 셸
database/         MySQL 스키마
scripts/          로컬 실행·API 점검·일부 주문 시나리오·DB 정합성 점검 도구
server/index.js    배포용 정적 서버
```

프론트는 2초마다 `/api/stocks`와 `/api/market-events`를, 호가·최근 체결 등 상세 데이터는 1초마다 조회한다.
백엔드에 WebSocket도 있지만 현재 웹·WebView 공통 화면의 시세 갱신은 REST 폴링을 사용한다.
로그인 상태에서는 Firebase ID
토큰을 `Authorization: Bearer ...`로 첨부해 포트폴리오·주문·관심 종목 API를 호출한다.

## 설계 방향 계약

- **대상/장면**: 애니·게임을 종목처럼 사고파는 사람이 시세를 훑고 주문한다. 표면 모드는 Operate(작업 완수)이며,
  Persuade(설득)가 아니다. 그래서 히어로·카피·CTA를 두지 않는다.
- **시각 명제**: 흰색 바탕 위에 자산 현황과 시세표를 보여 준다. 1px 괘선으로 구획을 나누고,
  상승 적색·하락 청색·브랜드 핑크를 상태와 선택 표시에 사용한다.
- **타입**: Pretendard(로컬 번들) 하나로 UI를 구성하고, 숫자는 tabular numerals를 쓴다.
- **시그니처**: 시세 값이 바뀔 때만 틱 플래시를 표시하고, 색으로 상승/하락 방향을 알린다.
  자동 스크롤·반복 루프·펄스 점은 쓰지 않는다.
- **모션**: 피드백(틱 플래시, 주문 결과)만. 섹션 등장 애니메이션 없음.
  `prefers-reduced-motion`에서는 플래시를 아예 만들지 않고 값만 갱신한다.
- **안티고백**: ① 네온 크립토 대시보드 ② 히어로+피처 카드+통계 스트립 랜딩 ③ 벤토+라운드 카드+알약 필터 대시보드.
- **폐기한 것**: 마케팅 히어로, 영문 eyebrow(GAME STOCK EXCHANGE·MARKET EVENTS·DISCOVER), 카드 중첩,
  장식용 반투명 도형, 알약 필터, 중복된 "실시간" 문구.

## 검증 기록

아래 기존 실행·화면 기록과 최신 구현 확인을 구분한다. 2026-09-30 문서 대조 작업 당시에는
서버 실행·빌드·로그인·거래 확인을 수행하지 않았고, 이후 같은 날 VI·서킷브레이커 구현 작업에서 로컬 실행을 재개했다.

- 이전 작업에서 `npm run typecheck`, `npm run build`를 통과했다.
- 정적 휴리스틱 감사(`frontend-apex` 스킬의 `audit_frontend.py`) 결과 0건.
  `outline: none` 2건과 9~10px 각인 배지는 코드에 사유를 남기고 예외 처리했다.
- 렌더 확인: 1440 / 900 / 390px에서 가로 오버플로 없음. 1080px 미만에서 2단→1단 전환,
  종목 상세가 목록 위로 이동, 전광판 열 수 축소, 터치 조작 34px 이상 확보.
- 공개 API 조회와 백엔드 연결 실패 시 대체 화면을 확인했다.
- **2026-09-27 로컬 실행 확인**: `scripts/start.ps1`로 웹과 백엔드를 시작했다. 웹 `http://localhost:5180/`은 HTTP 200,
  백엔드 `http://localhost:8081/api/health`는 `{"status":"ok"}`를 반환했고 당시 MySQL 서비스도 실행 중이었다.
- 이후 로컬 웹·백엔드를 종료하고 로컬 MySQL의 `gamestock` 스키마를 삭제했다.
  2026-09-30 VI·서킷브레이커 추가 후 `database/schema.sql`로 로컬 스키마를 다시 생성했다.
- **2026-09-30 구현·실행 확인**: 웹 빌드와 백엔드 컴파일·기동을 확인했다.
  웹 `http://localhost:5180/`은 HTTP 200, 백엔드 `/api/health`는 `{"status":"ok"}`를 반환했다.
  `/api/stocks`의 종목별 `restriction`과 `/api/market-status`의 가상 지수·거래일 응답을 확인했다.
  실제 계정의 VI·서킷브레이커 발동부터 단일가 체결·재개까지와 실제 휴대폰 터치 동작은 아직 검증하지 않았다.
- **2026-09-30 동적 VI 반복 수정**: 로컬 니케(GOV)가 같은 21,300원 기준으로 반복 발동하는 이력을 확인했다.
  체결 없이 재개할 때 동적 기준을 갱신하도록 수정하고, 기존 체결 이력을 보존했다.
  서버 반영 후 VI 해제·봇 체결 재개와 이후 2분 이상 새 VI 이력이 늘지 않는 것을 DB·API·시장 화면에서 확인했다.
  장기 거래와 실제 사용자 주문을 포함한 통합 검증은 남아 있다.
- **2026-09-30 봇 시각·보유 영역 수정**: 로컬 서버에서 10개의 독립 봇 스케줄(3종목의 매수·매도 봇 6개 + 참여자 4명)이 실행되는 것을 확인했다.
  서버 반영 뒤 저장된 주문·체결 시각이 기존 5초 간격에 고정되지 않는 것을 확인했다.
  웹·앱 공통 스타일의 종목 상세 `내 보유`는 호가·최근 체결 두 칸 전체 너비를 사용한다.
  공통 패널과 예시 보유값으로 데스크톱 오른쪽 끝 정렬과 390px 화면의 가로 넘침 없음을 확인했다. 실제 로그인 계정·실제 기기 확인은 남아 있다.
- 이 실행 확인은 로그인·주문·체결·새로고침 후 자산 유지까지의 브라우저 통합 테스트나 Railway 운영 배포 검증을 포함하지 않는다.
- **다음 검증**: 실제 Google 로그인부터 주문·체결·잔고 유지까지 확인하고, 거래 품질·DB 정합성·Railway 환경을 최신 상태로 점검한다.

## 기본 요구사항 및 구현 현황

기능 체크리스트의 `[x]`는 소스에서 구현을 확인한 범위를 뜻하며, 현재 환경에서의 정상 동작을
모두 검증했다는 뜻은 아니다. `[ ]`는 미구현 또는 보완이 필요한 작업이다.
아래 보완 계획의 문서·도구 작성 완료와 실제 실행 결과는 별도로 구분한다.

### 서비스 요구사항

- 게임을 가상 종목으로 상장하고, 실제 게임 뉴스와 이용자 거래를 가격 형성에 반영한다.
- 로그인하지 않아도 시장·뉴스·랭킹·한강 수온 등 공개 화면을 조회할 수 있어야 한다.
- Google 로그인 사용자는 개인 현금·보유 종목·주문·체결 내역을 관리할 수 있어야 한다.
- 사람과 봇의 주문을 호가창에서 가격·시간 우선으로 매칭하고, 체결 결과를 즉시 반영한다.
- 유동성 봇은 양쪽 호가를 공급하며 거래량·뉴스·난수에 따라 주문량을 조절한다.
  주문당 수량 상한은 일반 주문 900주, 대량 주문 1,800주이며, 봇 가격은 당일 기준가 대비 ±20% 범위로 제한한다.
  종목별 매수·매도 봇은 각각 독립적으로 3~18초 사이의 다음 행동 시각을 정한다. 밀리초 단위로 간격을 뽑으며 매번 다시 정한다.
- 일반 사용자 주문 경로로 거래하는 참여자 봇 4명을 별도로 두며, 각각 모의 자금 100만원으로 시작하고 랭킹에 포함한다.
  참여자 봇도 각각 독립적인 8~40초 행동 간격을 사용한다. 지정가의 실제 체결 시점은 상대 주문이 들어오는 시점에 달려 있다.
- 웹과 Android/iOS 앱이 같은 Spring Boot·MySQL 백엔드를 사용해야 한다.
- 실제 금융상품이 아닌 교육·관찰 목적의 가상 시장임을 화면에 명시한다.

## 외부 데이터 연동 요구사항

### 게임 뉴스

현재 기본 3종목의 Google News RSS와 공식 X 공개 타임라인을 서버 시작 시와 10분마다 조회하도록 구현돼 있다.
RSS 기사는 `미디어 보도`, 게임별 공식 X 계정 글은 `업데이트 노트`로 저장한다.
종목명만 포함된 RSS 오탐은 제외하고, 공식 X 글은 계정 자체를 종목 경계로 삼는다.

- 공통 화면의 `/api/market-events`는 종목별로 미디어 보도·업데이트 노트를 각각 최신 2건씩 선별한다.
  3종목 기준 최대 12건이며, 전체 10건으로 고정하지 않는다.
- 메인은 미디어 보도 최대 6건을 표시한다. 뉴스 화면과 종목 상세는 공통 응답을 필터링한다.
- 별도 `/api/stocks/{stockCode}/news`는 종목별 최대 5건이지만 현재 공통 화면의 조회 경로는 아니다.
- 가격 계산은 최근 24시간의 종목별 관련 뉴스 최대 10건을 사용한다. 영향도는 -10~+10이다.
- 현재 뉴스 제목은 종목 화면으로 이동한다. 요약 상세 화면·원문 링크 연결은 추가 작업이다.
- 외부 피드별 수집 실패를 처리하고 기존 저장값을 유지하는 코드가 있다. 최신 RSS·X 수집 성공 여부는 실행 검증이 필요하다.

#### VI·서킷브레이커 적용 규칙

한국거래소의 [VI 안내](https://regulation.krx.co.kr/contents/RGL/03/03010409/RGL03010409.jsp)와
[서킷브레이커 안내](https://regulation.krx.co.kr/contents/RGL/03/03020402/RGL03020402.jsp)를 참고해
24시간 가상 시장에 적용한다. 실제 거래소의 전체 예외·주문 유형을 재현하는 구현은 아니다.

| 장치               | 발동 기준                                                                   | 효과                                                      |
| ------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------- |
| 동적 VI            | 직전 체결가 또는 VI 재개 기준가 대비 예상 체결가 ±6% 이상                   | 해당 종목 2분간 즉시 체결 중단·지정가 접수 후 단일가 체결 |
| 정적 VI            | 거래일 시작 기준가 또는 직전 단일가 대비 ±10% 이상                          | 해당 종목 2분간 지정가 접수 후 단일가 체결                |
| 서킷브레이커 1단계 | 가상 지수 8% 이상 하락, 1분 지속                                            | 전체 시장 20분 중단 후 10분 지정가 접수·단일가 체결       |
| 서킷브레이커 2단계 | 1단계 재개 후 15% 이상 하락·직전 발동 지수 대비 1% 이상 추가 하락, 1분 지속 | 전체 시장 20분 중단 후 10분 지정가 접수·단일가 체결       |
| 서킷브레이커 3단계 | 2단계 재개 후 20% 이상 하락·직전 발동 지수 대비 1% 이상 추가 하락, 1분 지속 | 한국시간 자정까지 전체 시장 신규 주문·체결 중단           |

- 가상 지수는 서버의 전체 종목 가격을 거래일 기준가로 나눈 값을 동일가중 평균하며 기준은 1,000이다.
  한국시간 날짜가 바뀌면 현재 가격으로 기준을 갱신한다. 최초 도입 시에도 현재 가격으로 초기화한다.
- 각 서킷브레이커 단계는 한국시간 거래일마다 한 번씩 순서대로 발동한다. 발동 시 기존 종목 VI를 해제하고 시장 전체 제한을 우선한다.
- 단일가 접수 중에는 지정가 접수·취소를 허용하고 시장가를 제한한다. 중단 구간에는 신규 주문을 거절하고 기존 주문 취소만 허용한다.
  3단계에도 주문 취소를 허용하며, 정규장 마감 직전 예외·랜덤 종료·가격제한폭에서의 수량 우선 배분은 적용하지 않는다.
- 단일가 가격은 체결 가능 수량 최대 → 매수·매도 잔량 차이 최소 → 현재가에 가까운 가격 순으로 정한다.
  같은 가격에서 가격·시간 우선으로 체결하고, 체결되지 않은 지정가는 유지한다. 교차 주문이 없으면 체결 없이 재개한다.
- 가상 시장은 체결 없이도 2분 뒤 재개하므로, VI 종료 시 재개 가격을 동적·정적 VI 기준으로 갱신한다.
  실제 마지막 체결가는 별도로 보존하며, 이후 체결이 발생하면 동적 기준을 그 체결가로 갱신한다.
  기존 기준가와 시세의 같은 차이로 VI가 반복되는 것을 막는 프로젝트 적용 규칙이다.
  새로운 급등락에는 다시 발동할 수 있고 하루 발동 횟수 제한은 없다.
- 실제 체결은 기준을 넘는 체결 직전에 VI를 발동한다. 뉴스에 의한 직접 시세 변경도 급변 기준을 확인하고 이후 변경·체결을 멈춘다.
- 발동 중 자동 뉴스 가격 변경과 봇의 즉시 체결도 멈춘다. 단일가 접수 구간에는 유동성 봇도 지정가만 공급한다.
- 상태와 종료 시각은 DB에 저장한다. 서버가 다시 시작되면 저장한 시각을 기준으로 단계 전환·단일가 마감을 처리한다.
  상태 갱신과 자동 재개는 5초 주기의 시장 관리와 각 주문 처리에서 이루어진다. 봇 주문은 별도의 랜덤 시각에 실행된다.
- 뱃지는 발동 중인 종목 목록·뉴스·보유 종목·종목 상세에 나타난다. 웹에서는 호버 또는 클릭, 앱에서는 터치하면
  발동 이유·거래 효과·남은 시간·단일가 또는 재개 예정 시각을 보여 준다. 앱 셸은 유지한다.

## 졸업 프로젝트 보완 계획

핵심 주문·체결·자산 관리 기능은 구현돼 있으며, 일부 화면 연결·부가 기능 보완과 최신 이용 흐름 검증은 남아 있다.
졸업작품에서는 **실제 게임 뉴스와 참여자 거래가 함께 가상의 게임주 가격을 만드는 과정을 구현·관찰하는 플랫폼**이라는 점을 중심으로 검증한다.

### 1. 문제 정의와 사용자 가치

- 프로젝트 정의: 실제 게임 뉴스를 바탕으로 사람과 봇이 거래하고, 뉴스 영향과 투자 행동이 최종 가상 게임주 가격을 결정하는 참여형 시장 시뮬레이션 플랫폼
- 목표 핵심 흐름: `실제 게임 뉴스 수집 → 관련성·영향도 분석 → 사람·봇 매수·매도 → 호가·체결 → 최종 가상 주가와 변동 이유 표시`
  (변동 이유 API는 구현, 현재 공통 화면의 설명 표시는 미연결)
- 해결 문제: 게임 뉴스가 투자자 심리와 게임 가치에 미치는 영향, 그리고 그 심리가 거래·가격으로 이어지는 과정을 한눈에 확인하기 어려움
- 핵심 사용자: 게임 이용자·관심자, 게임사·퍼블리셔, 게임산업 분석가·투자자
- 제공 가치: 뉴스·거래량·호가·가격을 한 흐름으로 확인하고, 특정 이슈에 대한 참여자 반응을 관찰
- 현재 가격 형성: 뉴스 직접 가격 반영, 사람·봇의 주문 매칭, 체결 VWAP와 유동성 봇 변동 제한을 규칙으로 결합
- 현재 구현: 최근 24시간 뉴스·거래·호가 근거를 `/api/stocks/{stockCode}/price-drivers`로 계산한다.
  현재 웹·WebView 종목 화면은 이 API를 조회하거나 설명을 표시하지 않는다.
  유동성 봇은 랭킹에서 제외하고, 일반 주문 경로를 쓰는 참여자 봇 4명은 랭킹에 표시한다.
- [ ] 가격 변동 설명 API를 웹·앱 공통 종목 화면에 연결
- 졸업 프로젝트 연관성: 뉴스 감성 분석, 거래 매칭 엔진, 실시간 데이터 처리, 가격 형성 모델, 시각화를 하나의 서비스 흐름으로 통합
- 투자받을 이유: 게임산업의 기대와 반응을 관찰할 수 있는 특화 데이터를 만들고, 장기적으로 게임사·분석 조직용 대시보드·리포트·API로 확장
- 한계: 가상 주가는 실제 금융상품의 가격이나 수익을 보장하지 않으며, 사업성은 공개 게임 지표·실제 이용자 반응과의 추가 검증이 필요
- 성공 기준: 사용자가 뉴스→거래→가격 변화를 이해하고, 데이터 흐름이 일관되게 재현되며, 게임사·분석가 관점에서 시장 반응을 확인하는 데 유용한지 테스트·인터뷰로 검증

## 메모용

### 현재 고민

1. 왜 이 서비스에 투자해야 하는가? 게임사와 협업하지 않는 비공식 서비스만으로는 메리트가 부족할 수 있다. 협찬이 생기면 주간 수익 1·2·3위 사용자에게 소정의 보상을 제공하는 방안을 검토한다.
   - 대상 사용자는 서브컬처 게임을 좋아하면서 주식 경험도 해보고 싶은 사람으로 설정하고, 교육·관찰용 서비스로 방향을 잡는다.
2. 실제 사용자가 얻는 혜택은 무엇인가?
   - 실제 주식 투자 전에 손실을 줄이고 투자 판단을 공부할 수 있다.
   - 주간 랭킹 우수 사용자에게 프로필 꾸미기 아이템이나 칭호를 제공해 반복 이용 동기를 만든다.
3. 개별 기능은 구현되었지만 전체 서비스로서 목적과 반복 이용 이유가 부족할 수 있다.
   - 뉴스·거래·가격의 인과관계를 관찰하고 비교하는 졸업 프로젝트의 실험·교육 목적을 전면에 둔다.

### 우선적으로 추가하면 좋은 기능

1. 메인 화면에서 게임 뉴스와 가격 변동 이유를 함께 표시한다.
   - 현재 뉴스와 소식 이후 가격 변화율은 표시한다. 가격 변동 이유 API의 화면 연결은 남아 있다.
   - 뉴스 제목을 누르면 요약과 가격 영향 방향을 보여 주고, 상승은 빨간색·하락은 파란색으로 구분한다.
     현재 제목 클릭은 해당 종목 화면으로 이동한다.
2. 1~2주 단위 시즌제와 시즌별 랭킹을 도입한다.
   - 시즌 종료 후 초기화 여부와 기존 자산 유지 여부를 결정한다.
3. 기본 미션의 실제 수행 확인을 보완하고, 특정 수익률 달성·손실 제한 등 투자 미션을 추가한다.
   - 현재 시장 보기·뉴스 읽기·관심종목 미션은 버튼 클릭 시 보상을 요청하며 실제 수행 여부를 서버에서 확인하지 않는다.
   - 프로필과 랭킹에 표시되는 칭호를 보상으로 제공하는 방안을 검토한다.
4. 뉴스·거래량·시장 이벤트·봇 거래가 가격에 준 영향을 설명한다.
   - 구현된 `/price-drivers`의 뉴스 영향도·거래량·호가 불균형 근거를 공통 화면에서 보여 주고 확장한다.
5. 친구나 커뮤니티에 올릴 수 있는 투자 성적 공유 카드를 제공한다.
   - 포트폴리오와 시즌 성적을 이미지 카드로 저장·공유하는 기능을 검토한다.

## 실제 주식시장과 GameStock의 차이

GameStock은 실제 투자를 대체하는 서비스가 아니라, 게임 뉴스와 참여자 거래가 가상 게임주 가격에 미치는 영향을 관찰하는 시장 시뮬레이션이다. 따라서 주문·호가·체결 같은 시장 구조는 참고하지만, 법적·금융적 효력은 실제 주식시장과 다르다.

### 자산과 소유권

- 실제 주식시장: 실제 기업의 주식과 현금이 거래되며 법적 소유권이 발생한다.
- 내 프로젝트: 게임 종목을 기반으로 만든 가상 주식과 모의 현금만 사용하며 실제 소유권이 없다.

### 종목과 정보

- 실제 주식시장: 상장 기업의 공시, 재무제표, 산업·거시경제 정보가 가격에 반영된다.
- 내 프로젝트: 게임별 RSS 뉴스, 관련성 필터, 긍정·부정 영향도(-10~+10)를 중심으로 가격을 계산한다.

### 가격 형성

- 실제 주식시장: 실제 투자자·기관·시장조성자의 주문, 수급, 기업가치, 시장 심리가 함께 가격을 결정한다.
- 내 프로젝트: 사용자 주문, 봇 유동성, 호가 불균형, 체결 VWAP, 최근 뉴스 영향도를 규칙 기반으로 결합한다.

### 거래 참여자

- 실제 주식시장: 실명·본인확인 절차를 거친 다양한 투자자가 참여한다.
- 내 프로젝트: Firebase Google 로그인 사용자, 내부 유동성 봇, 모의 자금 100만원으로 시작하는 참여자 봇 4명이 참여한다.
  참여자 봇은 사용자와 같은 주문 경로를 쓰고 랭킹에 포함되며, 유동성 봇은 랭킹에서 제외한다.

### 거래 시간

- 실제 주식시장: 거래소별 정규장·시간외시장·휴장일·거래정지 규칙이 있다.
- 내 프로젝트: 기본 24시간 거래하며 VI·서킷브레이커 발동 시 제한한다. 정규장·시간외시장·휴장일 구분은 없다.

### 주문과 체결

- 실제 주식시장: 거래소의 가격·시간 우선 원칙, 시장가·지정가·부분 체결, 각종 주문 제한이 적용된다.
- 내 프로젝트: 시장가·지정가·부분 체결·주문 취소와 가격·시간 우선 매칭을 구현했지만, 거래소의 모든 주문 유형과 예외 규칙을 포함하지 않는다.

### 결제와 자금

- 실제 주식시장: 증권·현금의 결제 주기, 예수금, 담보, 증거금, 세금·수수료 규칙이 적용된다.
- 내 프로젝트: 체결 즉시 가상 현금과 보유 수량을 반영한다. 매수·매도 체결 금액에 0.10% 수수료를 적용하며 세금은 구현하지 않았다.

### 가격 제한과 안정장치

- 실제 주식시장: 거래소별 가격제한폭, 서킷브레이커, 변동성 완화장치, 시장감시가 적용된다.
- 내 프로젝트: 당일 기준가(일별 시가) 대비 ±30% 제한폭을 사용한다.
  유동성 봇은 ±20% 내부 범위와 틱별 변동 제한을 적용한다.
  종목별 VI와 시장 전체 서킷브레이커의 발동·주문 제한·단일가 재개를 구현한다.
  가상 지수·한국시간 거래일·지정가만 받는 단일가 등 위 적용 규칙을 사용한다.

### 뉴스 반영

- 실제 주식시장: 공시·실적·정책·속보가 시장 참여자의 해석과 주문을 통해 간접적으로 가격에 반영된다.
- 내 프로젝트: 최근 관련 뉴스 10건과 24시간 누적 영향도를 규칙으로 계산하고, 뉴스의 직접 가격 영향과 거래 영향을 함께 반영한다.

### 사용자 기능

- 실제 주식시장: 투자 성과는 금융기관 계좌와 세금·수수료 내역을 기준으로 관리된다.
- 내 프로젝트: 랭킹, 마이페이지, 인생 리셋 등 학습·관찰·게임화를 위한 기능이 제공된다.

### 규제와 위험

- 실제 주식시장: 금융위원회·거래소·증권사의 규제, 투자자 보호, 이상거래 감시를 받는다.
- 내 프로젝트: 교육·연구용 가상 서비스이며 금융상품 판매, 투자 권유, 수익 보장을 하지 않는다.

### 차이를 해석하는 기준

- **비슷한 부분**: 호가창, 시장가·지정가 주문, 부분 체결, 체결 가격, 거래량, 뉴스에 따른 심리 변화 등 시장의 관찰 가능한 흐름을 단순화해 재현한다.
- **다른 부분**: 실제 기업의 가치·공시·거시경제·법규·실명 투자자·실제 자금이 없고, 뉴스와 봇의 움직임이 규칙 기반으로 설계되어 있다.
- **프로젝트의 목적**: 실제 수익률을 재현하는 것이 아니라 `게임 뉴스 → 참여자 반응 → 주문·체결 → 가상 가격`의 인과관계를 확인하고 설명하는 것이다.
- **이용 주의**: GameStock의 가격·랭킹·수익률은 실제 투자 판단이나 미래 수익을 의미하지 않는다.
