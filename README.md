# 슈엔증권 (GameStock)

> **이 서비스에 사용된 모든 저작물의 소유자는 각 게임사 및 제작사에 있으며 비영리의 목적으로 운영됨을 알려드립니다.**

**내가 좋아하는 게임에 투자해 그 게임의 값을 올리는 모의 주식 게임.**

서브컬처 게임 15종을 가상 주식 종목으로 상장했습니다. 사용자는 모의 자금 100만원으로 게임 주식을 사고팔고, 실제 게임 뉴스와 다른 투자자들의 주문이 가격을 움직이는 과정을 실시간으로 지켜봅니다. 서비스 이름은 **슈엔증권**, 저장소와 백엔드 프로젝트 이름은 **GameStock**입니다.

- 웹: https://gamestock-20994.web.app
- API: https://gamestock-api.161-33-33-45.sslip.io (상태 확인 `/api/health`)
- 모바일: Expo(React Native) 앱, Android·iOS 대상

> 모의 투자 서비스입니다. 실제 주식·현금·게임 재화를 거래하지 않으며, 화면의 모든 금액은 가상 자금입니다.

## 만든 의도

서브컬처 게임 팬들은 자기가 하는 게임에 대한 애정이 큽니다. 커뮤니티에서는 "우리 게임이 더 잘나간다"는 이야기로 자주 경쟁이 붙습니다. 슈엔증권은 그 경쟁을 **주식 시장**으로 옮겨 왔습니다.

- **내 게임을 사서 값을 올린다.** 좋아하는 게임의 주식을 많은 사람이 사면 실제 매수 주문이 호가를 소화하면서 가격이 오릅니다. 팬덤의 응원이 숫자로 보입니다.
- **게임끼리 경쟁이 붙는다.** 홈 화면의 시장 지도와 "오늘 많이 움직인 종목"에서 어떤 게임이 오르고 내리는지 바로 비교할 수 있습니다. 대형 업데이트나 논란 같은 실제 뉴스도 가격에 반영됩니다.
- **투자 실력도 겨룬다.** 순자산 랭킹과 주간 수익률 랭킹, 칭호가 있어서 "어떤 게임을 언제 샀는가"로 다른 사용자와 겨룹니다.
- **시장이 어떻게 움직이는지 배운다.** 가격은 난수가 아니라 호가와 체결로 정해집니다. 뉴스 → 주문 → 호가 → 체결 → 가격으로 이어지는 흐름을 직접 관찰할 수 있도록 만들었습니다.
- **보상 체계** 실제 금전같은걸 걸수는 없으니 게임 이용 시 제공되는 칭호로 수집욕구를 자극시키려는 의도가 있습니다.

사람이 적은 시간에도 시장이 비어 보이지 않도록, 서버에서 6,020명 규모의 전략 봇과 유동성 공급 봇이 사람과 같은 호가창에서 거래합니다. 봇은 가격을 정해 주는 장치가 아니라, 사람과 같은 규칙으로 주문을 내는 시장 참여자입니다. 자세한 내용은 [봇의 역할](#봇의-역할)에 있습니다.

## 핵심 흐름 한눈에 보기

```text
 실제 게임 뉴스(RSS)                 사람의 주문 (웹·앱)
        │                                   │
        ▼                                   ▼
 관련성 필터 → 영향 점수(-10~+10)     주문 접수·검증 (잔고·가격제한·VI)
        │                                   │
        ▼                                   ▼
 종목 내재가치·합의가치 갱신 ──▶ 봇 판단 ──▶ 같은 호가창에서 가격·시간 우선 매칭
                                            │
                                            ▼
                               체결 → DB 커밋 → 현재가 변경
                                            │
                                            ▼
                     WebSocket으로 시세·호가·체결·내 계좌 전송 (웹·앱)
```

**현재가는 실제 체결로만 바뀝니다.** 뉴스나 봇이 가격을 직접 써넣지 않습니다. 뉴스는 봇이 생각하는 적정 가치를 바꾸고, 그 생각이 주문이 되고, 주문이 체결될 때 비로소 가격이 움직입니다.

```text
┌──────────── 웹 (React) ─────────────┐   ┌──────── 모바일 (Expo) ────────┐
│ Firebase 로그인 → ID 토큰            │   │ 네이티브 탭 · 딥링크 로그인    │
└──────┬──────────────┬───────────────┘   └──────┬──────────────┬─────────┘
       │ REST /api/*   │ WebSocket /ws/stream       │ REST          │ WebSocket
       └───────────────┴──────────────┬─────────────┴───────────────┘
                                      ▼
                 Nginx (HTTPS·WSS) ─▶ Spring Boot (OCI VM, 127.0.0.1:8081)
                 ├─ 주문 접수 → 메모리 호가 매칭 → 배치 DB 저장 (영수증으로 중복 방지)
                 ├─ 봇 스케줄러: 4개 종목 그룹, 접속자 있을 때만 상시 매칭
                 ├─ 거래 보호: 가격제한폭 · VI · 서킷브레이커 · 단일가
                 ├─ 뉴스 수집(10분) · 본문 발췌 · 영향 분석
                 ├─ 대출 이자·담보 감시, 주간 랭킹·칭호, 미션
                 ├─ 공개 시세 캐시 (변경 시에만 DB 재조회)
                 └─ 오래된 데이터 정리 (무료 DB 용량 유지)
                                      │ TLS, 사설망
                                      ▼
                          MySQL (OCI, gamestock 스키마)
```

- 웹과 앱은 같은 백엔드, 같은 실시간 스트림, 같은 Firebase 인증을 사용합니다.
- 로그인하지 않아도 시장·종목·뉴스·랭킹을 볼 수 있습니다. 주문과 계좌 화면에는 로그인이 필요합니다.
- 실시간 연결이 끊기면 웹은 지수 백오프(최대 15초)로 재연결하고, 연결 상태를 확인하는 하트비트와 4분마다 인증 갱신을 보냅니다.

## 기능이 돌아가는 원리

### 1. 주문과 매칭

1. 주문이 들어오면 서버가 종목·수량(1~1,000주)·주문 유형을 검증하고, 거래 보호 상태(VI·서킷브레이커·거래 정지)를 확인합니다.
2. 사람 주문은 전용 접수 큐에 쌓이고, 2ms 동안 모인 주문을 최대 200건까지 한 트랜잭션으로 처리합니다. 봇 주문보다 먼저 처리됩니다.
3. 매칭은 **가격 우선, 같은 가격이면 시간 우선**입니다. 매수 지정가는 그 가격 이하의 매도 호가와, 시장가는 실행 범위(기준가 ±10%) 안의 가장 좋은 호가와 체결됩니다. 체결되지 않은 지정가 수량은 호가창에 남습니다.
4. 매수 주문은 필요한 현금을 **예약**하고, 매도 주문은 보유 수량을 예약합니다. 미체결 주문을 취소하면 예약이 풀립니다. 그래서 같은 돈이나 주식을 두 번 쓸 수 없습니다.
5. 체결 결과는 **DB에 커밋된 뒤에만** 성공으로 응답합니다. 주문 배치마다 영수증을 함께 저장해서, 커밋 응답이 유실돼 다시 시도하더라도 주문이 두 번 실행되지 않습니다.

### 2. 가격이 정해지는 방식

- 현재가는 **마지막 체결가**입니다. 체결이 없으면 가격도 그대로입니다.
- 각 종목에는 실제 게임 이용자 규모를 본뜬 가상 규모(시가총액·유동성)가 있습니다. 대형주 8개는 천천히, 소형주 7개는 크게 움직입니다. 이 수치는 시뮬레이션 입력값이며 실측 통계가 아닙니다.
- 봇은 **합의 가치**(시장 참여자들이 생각하는 적정가) 주변에서 호가를 냅니다. 합의 가치는 종목 규모에 맞춘 무작위 걸음으로 조금씩 움직이고, 시장 국면을 따라 흐르며, 뉴스가 바꾼 목표가 쪽으로 수십 분에 걸쳐 끌려갑니다. 뉴스가 나오자마자 가격이 순간이동하지 않는 이유입니다.
- 게임주 지수는 15개 종목을 시가총액 비중으로 담은 지수 ETF(`ETFIDX`)의 NAV입니다. 처음 1000에서 시작했고, 자정에 다시 1000으로 돌아가지 않고 전날 종가에서 이어집니다. 등락률은 전날 종가 대비이고, 선물·옵션도 이 지수를 따릅니다.

### 3. 뉴스 분석

1. **수집**: 10분마다 종목별 Google 뉴스 RSS를 가져옵니다(게임 이름으로 검색 주소를 자동 생성).
2. **관련성 필터**: 제목·본문이 그 게임에 관한 기사인지 규칙으로 판별하고, 같은 기사의 중복 게재를 하나로 묶습니다.
3. **영향 점수**: 가중 키워드 규칙으로 -10~+10 점수를 매깁니다. 대규모 업데이트·흥행·매출 증가는 양수, 서비스 장애·논란·소송은 음수입니다. 생성형 AI나 학습된 예측 모델은 쓰지 않습니다.
4. **본문 발췌**: 원문 주소를 풀어 기사 첫 문단을 미리 저장해 둡니다. 화면에서는 저장된 발췌를 바로 보여 줍니다.
5. **가격에 미치는 경로**: 최근 24시간 안의 관련 뉴스 10건이 시간이 지날수록 약해지는 가중치로 합산됩니다. 이 값이 종목의 내재가치와 합의 가치 목표를 움직이고, 뉴스 반응형 봇은 각자의 반응 지연 시간이 지난 뒤 주문을 냅니다.

뉴스 화면의 "발행 이후 가격 변화"는 다른 거래와 시장 요인도 포함한 값입니다. 그 기사 하나의 효과만 뜻하지 않습니다.

### 5. 실시간 전송

- 서버는 종목별로 직렬화한 스냅샷 하나를 만들어, 그 종목을 구독한 모든 연결에 같은 메시지를 보냅니다. 연결 수가 늘어도 종목당 계산은 한 번입니다.
- 내 계좌(잔고·보유·주문 상태)는 로그인한 연결에만 개인 채널로 보냅니다. 보유 종목 평가액은 2초마다 다시 계산하고, 바뀐 경우에만 보냅니다.
- 첫 화면이 기다리는 공개 시세·시장 상태·뉴스는 서버가 미리 계산해 둡니다. 체결이나 정비가 커밋됐을 때만 DB를 다시 읽고, 뉴스는 수집·발췌가 저장됐을 때만 다시 읽습니다.

### 6. 접속에 따라 바뀌는 시장 속도

- 웹·앱 접속(WebSocket 연결 또는 API 요청)이 있으면 **활성 모드**입니다. 4개 종목 그룹이 250ms 간격으로 봇 매칭을 돌리고, 종목당 초당 체결 목표에 맞춰 주문량을 정합니다.
- 마지막 접속 후 2분이 지나면 **유휴 모드**로 내려갑니다. 30분마다 짧은 매칭(배치 5회)만 하고, 쉬는 동안 밀린 체결을 나중에 몰아서 만들지 않습니다.
- 상태 확인(`/api/health`)과 봇 자신의 활동은 접속으로 치지 않습니다.

### 7. 정산과 계좌

- 체결 즉시 정산됩니다. 매수자는 주식을, 매도자는 대금을 바로 받습니다.
- 사람이 참여한 체결에는 매수·매도 각각 0.1% 수수료가 붙습니다.
- 총자산 = 현금 + 주문에 묶인 예약 현금 + 보유 종목 평가액 + ETF·파생 평가액 − 대출 잔액. 평가액은 최근 체결 흐름과 호가로 계산한 평가 가격(mark price)을 씁니다. 한 번의 튀는 체결로 자산이 출렁이지 않게 하기 위해서입니다.

### 8. 참여 기능

- **미션**: 매일 3개가 선정되고, 완료하면 건당 5만원의 모의 자금을 받습니다.
- **랭킹**: 전체 랭킹은 순자산 순입니다. 수익률에서는 출석·미션 보상과 관리자 지급액을 뺍니다. 주간 랭킹은 한국시간 월요일 0시 자산을 기준으로 수익률을 계산하고, 월요일 0시에 주간 칭호를 지급합니다. 봇·데모·관리자 계정은 제외합니다.
- **칭호**: 거래·자산·랭킹 조건을 달성하면 얻고, 하나를 장착하면 랭킹에 표시됩니다. 주간 칭호는 여러 번 받을 수 있습니다(n관왕).
- **대출**: 순자산의 50%까지 빌릴 수 있고(최소 1만원), 하루 0.1% 이자가 붙습니다. 담보비율이 140% 아래로 내려가면 경고와 함께 신규 대출이 막힙니다. 120% 아래로 내려가면 미체결 주문을 취소하고 시장가로 팔아 빚을 갚습니다(반대매매).

### 9. 무료 DB 범위를 지키는 데이터 정리

운영 DB는 OCI MySQL Always Free(스토리지 50GB, 백업 50GB)입니다. 용량이 계속 늘지 않도록 백엔드가 2분마다 한 번에 일정량씩 오래된 데이터를 정리합니다.

| 데이터                       | 보관 방식                                                                                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 가격 이력                    | 2일까지 원본. 2~8일은 분마다, 8일~1년은 시간마다 시가·종가·고가·저가 4점만 남김. 1년이 지나면 삭제. 차트 봉 단위가 이보다 크므로 차트 모양은 같습니다 |
| 봇끼리의 체결·정산·완료 주문 | 30일 후 삭제(유동성·지표 집계에 이미 반영된 것만)                                                                                                     |
| 봇 상세 체결 기록            | 초 단위 15분, 분 단위 8일, 시간 단위 370일                                                                                                            |
| 거래 제한 기록               | 90일                                                                                                                                                  |
| 주문 처리 영수증             | 1시간                                                                                                                                                 |

**사람이 참여한 체결·주문·정산 기록은 지우지 않습니다.**

### 10. ETF·선물·옵션

주식 계좌의 현금을 그대로 쓰는 모의 파생 상품입니다. 별도 파생 계좌는 없고, 평가액은 총자산과 랭킹에 포함됩니다. 계정을 초기화하면 열린 파생 포지션과 거래 원장도 함께 지웁니다.

| 상품 | 계약·가격 | 수수료 | 정산 |
| --- | --- | --- | --- |
| 카테고리 ETF | RPG·액션·FPS·얼터너티브 바스켓, NAV 1좌 | 0.1% | NAV 즉시 매매 |
| 지수 ETF | `ETFIDX`, 전 종목 시가총액 가중 | 0.1% | NAV 즉시 매매 |
| 지수 선물 | `FUTIDX` 무기한, 1계약=지수 1포인트×1,000원, 2x/5x/10x | 명목가 0.02% | 증거금 예약, 평가액이 증거금 10% 이하이면 강제청산 |
| 옵션 | 유럽형 콜·풋 매수, 행사가 5포인트 단위(지수 ±2%), 1계약=1포인트×1,000원 | 프리미엄 0.3% | 만기 내재가치 현금결제, 만기 전 프리미엄 청산 |

옵션 만기는 세 회차입니다.

- **10분 만기**: 매 10분 정각(`:00`, `:10`, …)에 만기되는 0DTE 성격의 회차
- **1시간 만기**: 매시 정각에 만기되는 주간 회차
- **일요일 18:00 만기**: 한국시간 일요일 18:00에 만기되는 월간 회차. 일요일 18:00이 지나면 다음 주 일요일로 넘어갑니다.

프리미엄은 무위험 이자율 0의 블랙-숄즈와 최근 지수 실현 변동성으로 계산합니다. 만기에는 콜 `max(0, 지수−행사가)`, 풋 `max(0, 행사가−지수)`의 내재가치로 현금결제합니다. API는 `GET /api/derivatives`(공개), `GET /api/derivatives/account`, `POST /api/derivatives/positions`, `POST /api/derivatives/positions/{id}/close`이고, 포지션은 `derivative_positions`, 원장은 `derivative_trades`에 저장합니다.

## 봇의 역할

봇은 **사람이 적어도 시장이 살아 있게 만드는 참여자**입니다. 가격을 직접 정하지 않고, 사람과 같은 호가창·같은 매칭 규칙으로 주문을 냅니다. 그래서 사람이 큰 매수 주문을 내면 봇이 내놓은 매도 호가를 실제로 소화하며 가격이 오릅니다.

### 참여자 봇 (기본 6,020명)

각자 하나의 종목을 맡고, 자기 전략과 성향(판단 주기, 반응 지연, 보유 기간, 위험 성향)에 따라 주문합니다.

| 전략 계열               | 예시 전략                                                | 성격                             |
| ----------------------- | -------------------------------------------------------- | -------------------------------- |
| 모멘텀                  | 빠른·느린 모멘텀, 돌파, 추세 추종, 눌림목, 거래량 모멘텀 | 오르는 쪽에 올라탐               |
| 역추세                  | RSI 역행, Z-점수, VWAP 회귀, 과열 소진, 급등 되돌림      | 과하게 움직이면 반대로           |
| 가치                    | 저평가 매수, 공격적·보수적 가치, 촉매 가치               | 내재가치보다 싸면 사고 비싸면 팜 |
| 단타                    | 스캘퍼, 호가 불균형, 미세 추세, 스프레드 테이커          | 짧은 시간의 작은 움직임          |
| 뉴스                    | 뉴스 반응, 뉴스 회의                                     | 뉴스에 반응하거나 일부러 반대로  |
| 스윙·노이즈·유동성 소비 | 스윙 추세, 무작위 흐름, 유동성 테이커                    | 다양한 주문 흐름 공급            |

- 신규 주문은 보통 5~10주이고, 최대 30초 동안 유효합니다. 살 돈이 부족하면 매수하지 않습니다.
- 봇은 자기 현금과 보유 주식 범위 안에서만 거래합니다. 돈을 새로 만들어 내지 않습니다.
- 한 종목 봇들의 돈이 바닥나 거래가 멈추지 않도록, 트레이더 봇은 하나의 **투자자 자금 풀**을 공유합니다. 30초마다 평균보다 많이 가진 봇의 여유 현금을 살 돈이 없는 봇에게 옮깁니다. 이때 전체 현금 합은 그대로이고, 주문에 묶인 예약 현금은 건드리지 않습니다.
- 봇의 일일 가격 범위는 ±20%로, 사람(±30%)보다 좁습니다. 소형주가 한계선에 가까워지면 추격 매매를 줄입니다.

### 유동성 공급 봇 (LP, 1개)

- 모든 종목에 매수·매도 호가를 최대 4단계, 단계당 최대 32주씩 냅니다. 사람이 언제 주문해도 상대 호가가 있도록 하는 시장 조성자입니다.
- 재고가 너무 많으면 팔고, 부족하면 다시 삽니다. 호가가 얇아지면 다음 정기 갱신을 기다리지 않고 바로 다시 채웁니다.
- 봇끼리 체결할 때 각 LP 호가의 마지막 1주는 사람 주문 몫으로 남겨 둡니다.
- LP가 번 순이익은 트레이더 자금 풀로 돌려보내서, 시장의 돈이 LP 한쪽에 쌓이지 않게 합니다.

### 봇 운영 원칙

- 봇끼리의 체결에는 수수료가 없습니다. 반복 거래로 시뮬레이션 자금이 사라지지 않게 하기 위해서입니다. 사람이 낀 체결에는 수수료가 정상적으로 붙습니다.
- 봇끼리의 체결은 개별 행 대신 초·분·시간 단위 집계로 저장해서 DB 쓰기를 줄입니다. 사람이 낀 체결은 일반 원장에 모두 남깁니다.
- 봇·데모·관리자 계정은 랭킹에서 빠집니다.
- 관리자는 봇 전체 또는 트레이더만 멈추거나, 매칭 주기와 종목당 체결 목표를 바꿀 수 있습니다. 트레이더를 다시 켤 때는 일부부터 서서히 늘리도록 설정할 수 있습니다.

## 로컬 실행

백엔드(8081)와 웹(5180)은 **동시에 실행해야 합니다.** 웹은 화면만 담당하고 시세·주문·로그인·잔고는 모두 백엔드 API에서 가져오므로, 둘 중 하나만 켜면 화면이 비거나 요청이 실패합니다. 아래 2번과 3번을 터미널 두 개에 나란히 띄워 두세요.

### 준비물

- Node.js 20.19 이상 또는 22.12 이상, npm
- Java 17, Maven 3.9 이상
- MySQL 8
- Firebase 프로젝트(Google·이메일/비밀번호 로그인 사용 설정)와 Firebase Admin 서비스 계정 키

### 1. 데이터베이스

새 개발 DB에서 한 번만 실행합니다.

```sql
SOURCE C:/path/to/GameStock/database/schema.sql;
```

`schema.sql`은 초기 생성용입니다. 이후에 추가된 테이블·컬럼·인덱스·기본 종목은 백엔드가 시작할 때 스스로 보완합니다. 마이그레이션은 DB 잠금으로 보호되어 서버 두 대가 동시에 실행하지 않습니다.

### 2. 백엔드 (터미널 1)

```powershell
$env:DB_URL = 'jdbc:mysql://localhost:3306/gamestock?useUnicode=true&characterEncoding=utf8&serverTimezone=UTC&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true'
$env:DB_USERNAME = '개발_DB_사용자'
$env:DB_PASSWORD = '개발_DB_비밀번호'
$env:FIREBASE_SERVICE_ACCOUNT_PATH = 'C:\path\to\firebase-admin.json'
$env:GAMESTOCK_CORS_ORIGIN = 'http://localhost:5180'

Set-Location backend
mvn spring-boot:run
```

API는 `http://localhost:8081`에서 열립니다. DB 세션은 UTC를 쓰고, 출석·미션·주간 집계 같은 서비스 날짜는 한국시간으로 계산합니다. `scripts/run-backend.ps1`은 루트 `.env`를 읽어 실행하지만, 특정 PC의 Java·Maven 경로에 맞춰져 있어서 다른 환경에서는 위 방법을 권장합니다.

### 3. 웹 (터미널 2)

백엔드를 띄운 **별도 터미널**에서 실행합니다. 저장소 루트에서 실행합니다.

```powershell
Copy-Item .env.example .env.local
npm ci
npm run dev
```

`.env.local`의 `VITE_API_BASE_URL`을 `http://localhost:8081`로, `VITE_FIREBASE_*`를 내 Firebase 프로젝트 값으로 바꿉니다. 웹은 http://localhost:5180 에서 열립니다.

두 서버가 함께 떠 있는지 확인합니다. http://localhost:5180 이 열리고 http://localhost:8081/api/health 가 `{"status":"ok",...}`를 반환해야 합니다. 웹만 켜져 있으면 화면은 뜨지만 시세·잔고·주문은 모두 실패합니다.

```powershell
npm run typecheck   # 타입 검사
npm run build       # dist/ 생성
npm run preview     # 빌드 결과 미리보기
```

`VITE_API_BASE_URL`이 비어 있으면 개발 모드는 `http://localhost:8081`을, 프로덕션 빌드는 운영 API를 씁니다. 주문을 시험하기 전에 어느 서버에 연결됐는지 꼭 확인하세요.

### 4. 모바일 앱

```powershell
Set-Location mobile
npm ci
# 로컬 백엔드를 쓸 때만 지정 (기본값은 운영 API)
$env:EXPO_PUBLIC_API_BASE_URL = 'http://PC의_LAN_IP:8081'
$env:EXPO_PUBLIC_WEB_APP_URL = 'http://PC의_LAN_IP:5180'
npm start
```

휴대폰에서 로컬 서버에 접속하려면 웹을 `npm run dev -- --host 0.0.0.0`으로 띄우고, 백엔드 CORS에 그 주소를 추가합니다.

## 배포와 운영

| 대상   | 방식                                                                                                                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 웹     | `main`에 푸시하면 `.github/workflows/firebase-hosting.yml`이 타입 검사·빌드 후 Firebase Hosting에 배포                                                                                                                         |
| 백엔드 | `backend/**`가 바뀐 채 `main`에 푸시하면 `.github/workflows/oci-backend.yml`이 Java 17 테스트·빌드 → 체크섬 검증한 JAR 전송 → 기존 프로세스 종료 → 새 버전 기동 → API·스케줄러·호가·HTTPS·WSS 확인. 실패하면 이전 JAR로 되돌림 |
| DB     | OCI MySQL HeatWave `MySQL.Free`(1 ECPU, 8GB 메모리, 50GB 스토리지), 사설망 TLS 연결, 하루 1회 자동 백업(1일 보관)                                                                                                              |
| 서버   | OCI VM(Oracle Linux 9 ARM64), `gamestock.service`(systemd), Nginx가 HTTPS와 `/ws/market`, `/ws/stream` 프록시                                                                                                                  |

- 매칭 엔진은 한 번에 하나만 실행합니다. DB 소유권 잠금으로 두 서버가 동시에 매칭하지 않게 막습니다.
- 서버의 논리 백업은 매일 한국시간 03:30에 만들고 7일 보관합니다.
- 무료 범위를 유지하려면 OCI 콘솔에서 DB 사양 변경, HeatWave 클러스터·고가용성·읽기 복제본 추가, 스토리지 자동 확장, 백업 보관 기간 연장을 하지 않아야 합니다. 비용이 생기면 바로 알 수 있도록 월 SG$1 예산을 만들어 두었습니다.
- 운영·백업·복구 절차는 [OCI 운영 문서](docs/oci-operations.md)에 있습니다. 예전 Railway 설정(`railway.json`)은 롤백 참고용으로만 남아 있습니다.

## 한계와 주의사항

- **모의 시장입니다.** 실제 돈·주식·게임 재화와 아무 관련이 없고, 투자 조언이 아닙니다.
- 종목 규모(이용자 수·시가총액)는 시뮬레이션용 입력값이며 실제 통계가 아닙니다.
- 뉴스 영향 점수는 키워드 규칙 기반이라 반어·문맥을 놓칠 수 있습니다.
- 봇의 체결 목표는 목표일 뿐 체결량이나 유동성을 보장하지 않습니다. 거래 정지·자원 부족·DB 지연 중에는 호가가 비는 순간이 생길 수 있습니다.
- 접속자가 없는 동안에는 시장이 거의 멈춰 있습니다. 의도한 동작입니다.
- 무료 DB(1 ECPU)를 쓰기 때문에 동시 접속이 아주 많으면 응답이 느려질 수 있습니다.
- `MarketConcurrencyTest`와 `MarketSimulationIntegrationTest`에는 이번 문서 작성 시점(2026-10-22) 기준으로 실패하는 사례 9개가 남아 있어 따로 확인이 필요합니다.
