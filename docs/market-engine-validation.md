# 거래 엔진·데이터 신뢰성 검증

GameStock의 거래 엔진은 주문 접수, 예약, 가격·시간 우선 매칭, 부분 체결, 즉시 정산, 취소·만료 반환을 하나의 DB 트랜잭션과 시장 잠금 안에서 처리한다. 검증 러너는 `scripts/test-market-quality.ps1`이다.

## 자동 시나리오

인증 토큰 없이도 다음을 자동 확인한다.

- 시장·뉴스·호가·체결·가격 이력·일봉 API가 200을 반환하는지
- 프로필·포트폴리오·주문·정산·주문 생성·취소·계정 초기화·관리자 API가 토큰 없이 401인지
- 종목별 뉴스가 최대 5건인지, 가격 설명의 현재가가 종목 API와 일치하는지
- 호가창에 매수·매도 배열이 존재하는지
- 각 HTTP 요청의 응답 시간을 측정하는지

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\test-market-quality.ps1
```

Firebase ID 토큰을 알고 있는 테스트 계정은 읽기 API까지 인증 상태로 점검할 수 있다.

```powershell
.\scripts\test-market-quality.ps1 -FirebaseIdToken $token
```

`-RunOrderScenarios`를 함께 지정하면 UMA 1주 지정가 주문을 현재가보다 충분히 낮게 접수한 뒤 취소하고, 예약 현금이 원래대로 돌아오는지 확인한다. 이 옵션은 실제 테스트 계정의 DB에 잠깐 주문을 만들므로 테스트 환경에서만 사용한다.

```powershell
.\scripts\test-market-quality.ps1 -FirebaseIdToken $token -RunOrderScenarios
```

## LP 유동성 공급

- LP의 기존 평가가치·실제 체결·재고 위험에 따른 가격 설정과 일반 봇의 뉴스·추세·손절 판단을 유지하고, 호가 보충 시점과 자원 배분을 보강한다.
- 배치 LP는 현재가에서 `max(1%, 4호가 단위)` 이내의 각 방향 잔량을 확인한다. 잔량이 14주 이하이고 추가 공급 가능한 현금·재고 및 위험 한도가 있으면 주기적 갱신 시각 전에도 보충한다. 먼 가격의 대량 주문은 이 판단에 포함하지 않는다.
- 현금·재고가 부족하면 가까운 가격에 체결 가능한 수량을 우선 배치하면서, 뒤쪽 단계에도 1주씩 남도록 배분한다. 최대 4단계, 단계별 최대 32주, 기존 자산·가격 제한을 지키며 자원을 새로 만들지 않는다.
- 호가 보충 자체로는 체결이나 주가 변화를 만들지 않는다. 자원이 소진되면 양방향 공급을 보장할 수 없으며, 기존 현금 재배분·재고 회복 정책의 한도를 따른다.

### 수요에 따른 공급과 정체 물량 회복

- 배치 LP는 자신의 호가를 제외한 가까운 매수·매도 잔량으로 수요를 판단한다. 같은 배치의 실제 체결이 있으면 공격 주문의 매수·매도 수량 비율 70%, 잔량 비율 30%를 사용한다. LP가 먼저 집행한 회복 체결은 수요 신호에서 제외한다. 이는 전체 시장의 30초 누적 거래량 지표가 아니다.
- 매수 우세이면 LP 매도 수량을, 매도 우세이면 LP 매수 수량을 최대 2.5배 늘린다. 반대쪽 기본 공급도 유지하며 단계별 최대 32주, 현금·주식·위험 한도는 그대로 적용한다. 비배치 LP 경로는 자신의 호가를 취소한 뒤 외부 잔량 비율을 사용한다.
- 배치 엔진에서 관측한 현재가가 60초간 같으면 같은 방향·가격에 쌓인 일반 봇 물량을 100주 이하로 제한한다. 오래된 주문부터 유지하고 초과 주문은 정상 취소하여 예약 자산을 반환한다. 사용자와 LP 주문은 이 정리 대상에 포함하지 않는다.
- 정체 중 새 봇 지정가 주문은 한 가격의 100주 한도를 넘으면 바깥쪽으로 최대 8호가 단위 분산한다. 가격 제한 안에 자리가 없으면 그 주문은 제출하지 않는다. 시장가 주문은 이 분산 대상이 아니다.
- 정체 상태에서 외부 최우선 호가에 200주 이상 남으면 회복 경로가 평가 기준의 0.5% 범위 내에서 초당 최대 15주(`BotProfile.MAX_ORDER_SIZE`)를 실제 매칭한다. 기존 일반 체결·재고 조절과 별도의 한도다. 우세 수요 쪽 물량을 먼저 확인하며, 매수 현금과 매도 재고의 비상 호가용 자산을 남긴다. 사용자 주문은 체결된 수량만 줄어든다.
- 가격 변화나 무접속 후 재개 시 정체 관측을 새로 시작한다. 주문 정리나 분산만으로 가격·체결을 기록하지 않으며, 자원 부족 또는 거래 보호 장치로 남은 물량 전부가 해소되지 않을 수 있다.

`LiquidityRecoveryPolicyTest`와 배치 엔진 회귀 테스트로 정체 시간, 우선순위, 예약 자산 반환, 재집중 방지, 사용자 주문 보존, 회복 체결·쿨다운·수수료·자산 보존을 검증한다.

회귀 테스트는 `MarketMakerLiquidityTest`, `BotActivityEngineTest.nearbyThinQuotesRefillBeforeDeadlineEvenWithLargeRemoteWalls`다. 운영 효과는 별도로 모든 종목의 현재가·가까운 양쪽 호가 잔량·최근 체결·LP 자산을 시간에 따라 관찰하고 실제 사용자 주문의 체결 가능성을 확인해야 한다.

`BotLiquidityRecoveryTest`는 15개 종목과 오래된 평가가치 0.5배·2배 조합을 검사한다. 보충 정책 변경에 따라 달라지는 봇 회전 횟수는 후반 체결이 계속되는지로 확인하고, 기존 참여자 자금으로 사람 계정을 구성해 종료 시점의 5주 매수·매도 실제 체결을 각각 검증한다. 현금·주식 보존, 음수 자산 금지 및 가격 제한 검사도 유지한다.

## 정합성 규칙

다음 조건은 DB에서 항상 참이어야 한다.

- `orders.remaining_quantity`가 0 이상이고 원래 수량을 넘지 않는다.
- `orders.reserved_cash`와 `reserved_quantity`는 지정가 미체결 잔량과 일치한다.
- `portfolios.quantity`·`settled_quantity`는 음수가 아니며 settled 수량은 보유 수량을 넘지 않는다.
- 체결이 취소되지 않았다면 `trades`와 연결된 `settlements`가 존재하고, 현재 구현의 체결 상태는 `SETTLED`다.
- 주문·체결·자산·수수료 갱신은 같은 트랜잭션에서 처리된다.
- `market_locks` 행 잠금으로 동시에 들어온 주문도 한 종목씩 직렬화된다.

운영 점검에서는 읽기 전용 SQL로 음수 잔고·음수 잔량·고아 외래키를 검사하고 결과를 배포 기록에 남긴다. 테스트 러너는 DB를 초기화하거나 임의의 거래 데이터를 삭제하지 않는다.

읽기 전용 정합성 검사는 다음 명령으로 실행한다. `.env`의 DB 접속 정보를 사용하며 비밀번호를 명령행이나 출력에 기록하지 않는다.

```powershell
.\scripts\check-market-invariants.ps1
```

## 응답 시간·실시간·재시작 측정

- API 러너의 `avgLatencyMs`와 개별 요청 시간을 저장한다. 발표용 기준은 개발 PC에서 공개 조회 API p95 1초 이하를 목표로 한다.
- WebSocket `/ws/market` 연결 직후 `MARKET_UPDATED` 수신 시각과 연결 시각의 차이를 측정하고, REST 가격과 payload의 종목 목록이 일치하는지 확인한다.
- `scripts/stop.ps1` 실행 후 `scripts/start.ps1`로 재기동하고 `/api/health`, `/api/stocks`, `simulation_state.tick`을 확인한다. 재기동 뒤 종목·뉴스·가격 이력이 유지되고 틱이 이어지면 복구 성공으로 기록한다.

현재 자동 점검에서는 공개 API 22개, 데이터 형태, WebSocket, 봇 가격 상한을 확인했다. Firebase ID 토큰을 제공하지 않은 실행에서는 개인정보·주문 변경 시나리오를 의도적으로 수행하지 않는다.
